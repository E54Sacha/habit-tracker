# Deploy the habit tracker

## How production fits together

| Part | Where | Deploys when | Settings |
|---|---|---|---|
| Front end (`web/`) | Vercel, project `habit-tracker` | every push to `main` (Vercel builds it itself) | `API_URL` = the Render URL, no trailing slash |
| API (`api/`, Docker) | Render, service `habit-tracker-api` (Frankfurt, free) | a push to `main` **once all GitHub Actions checks pass** (`autoDeployTrigger: checksPass` in `render.yaml`) | `DATABASE_URL` (Neon, direct connection), `JWT_SECRET` (generated by Render), `COOKIE_SECURE=true`, `ENVIRONMENT=production` |
| Database | Neon, project `habit-tracker` (Frankfurt, Postgres 17) | schema changes run by Alembic **every time the API container starts** (`alembic upgrade head` in the Dockerfile) | — |

Live URLs: site https://habit-tracker-zeta-sooty.vercel.app · API https://habit-tracker-api-tnwt.onrender.com (`/health`, `/docs`).

The browser only talks to Vercel: `/api/*` is forwarded to Render by the rewrite in `web/next.config.ts`, so the login cookie is first-party.

## Deploy

1. Make sure the work is committed and the tests pass locally: `docker compose up -d`, then `pytest` in `api/` and `npm run lint && npm run build` in `web/`.
2. `git push` to `main`.
3. Watch CI: `gh run watch --exit-status` (jobs: API tests, front end, Docker image, end-to-end, coverage badge).
   - Red CI: Render does **not** deploy the API. Vercel still deploys the front end, so fix fast or roll the front end back (below).
4. Render starts the deploy after green checks (about 3–5 minutes: Docker build, migrations, health check on `/health`). A failed health check keeps the previous version running.

**Never** put secrets in the repo or in this file: they live in the Render and Vercel dashboards (and Neon for the database password).

## Check the live app

1. `curl -s https://habit-tracker-api-tnwt.onrender.com/health` → `{"status":"ok"}` (this also checks the database). The free server sleeps after 15 minutes: the first call can take up to a minute.
2. `curl -s https://habit-tracker-zeta-sooty.vercel.app/api/health` → same answer, through Vercel's rewrite.
3. In a browser: home page → **Try it as a guest** → 4 demo habits with streaks and calendars; tick one, reload, it stays ticked.

## Roll back

Pick the smallest fix:

| Problem | Do this |
|---|---|
| Front end broken | Vercel → project → **Deployments** → the last good one → **⋯ → Promote to Production** (instant). Then fix and push. |
| API broken, no migration in the release | Render → service → **Events** → the last good deploy → **Rollback**. Then fix and push. |
| Any bad commit | `git revert <sha>` then `git push`: CI runs, then both sides redeploy the reverted code. Keeps history honest. |
| Migration broke the API | Prefer a new migration that fixes it ("roll forward"). Rolling back the API alone can leave a newer schema than its code expects. Only if the migration is safe to undo: run `alembic downgrade -1` against Neon from your machine (`DATABASE_URL` set only in that terminal), then roll the API back. |

After any rollback, run "Check the live app" again and say what was rolled back and why.

## Common failures

| Symptom | Likely cause |
|---|---|
| Render deploy fails on start | `alembic upgrade head` failed (read the deploy log), or `ENVIRONMENT=production` with a missing/short `JWT_SECRET` or `COOKIE_SECURE` not `true` (the app refuses to start on purpose). |
| Site loads but every action says "Can't reach the server" / 404 on `/api/...` | `API_URL` missing or wrong on Vercel, or set after the build: fix it, then **Redeploy** on Vercel (rewrites are fixed at build time). |
| Logged out right after logging in | Cookie not kept: check the API is called through `/api/*` on the Vercel domain, not the Render URL directly. |
| `/health` 500 | Database unreachable: Neon project paused or `DATABASE_URL` changed. |
